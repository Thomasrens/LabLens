# LabLens: An AR-Style Assistant for Safe Laboratory Equipment Use

## Abstract

LabLens is a mobile-first web application intended to support students as they identify common laboratory instruments, learn their major parts and follow structured, safety-aware operating guidance. The prototype combines an optional image classifier, QR-code identification and a manual equipment library. Equipment instructions are stored in a validated JSON dataset rather than generated by an AI model. A camera view provides a 2D alignment silhouette and labeled hotspots, followed by sequential instructions, safety acknowledgements, a knowledge quiz and a local feedback survey. The system is designed as an educational aid and does not replace instructor supervision, equipment manuals or institutional standard operating procedures. The project evaluates technical reliability, recognition performance, task completion, procedural errors, quiz outcomes and usability.

## 1. Introduction

Laboratory learning requires students to understand equipment components, operating sequences and hazards before carrying out practical work. Paper manuals and demonstrations remain important, but students may find it difficult to connect written descriptions to the physical instrument during a practical session. A camera-enabled, mobile field guide can make part identification and procedural reminders accessible at the point of use. LabLens explores this approach using browser technologies that are easy to host and extend.

## 2. Problem statement

Students may have limited access to concise, instrument-specific instructions at the laboratory bench. Inconsistent familiarity with parts, controls and safety checks can lead to confusion, delays and avoidable procedural errors. A lightweight system is needed to identify selected equipment, display instructor-reviewed information and guide students through a repeatable learning sequence without allowing a generative model to invent laboratory instructions.

## 3. Objectives

1. Develop a responsive browser application that runs without a build tool.
2. Provide three identification paths: optional image classification, QR scanning and manual selection.
3. Store all instructional content in a structured JSON file and validate it at load time.
4. Display labeled parts using a 2D camera-aligned overlay.
5. Guide users through ordered steps and require acknowledgement of safety warnings.
6. Assess understanding using a multiple-choice quiz and score summary.
7. Collect user experience feedback and export it as CSV.
8. Support dark mode, text-size settings, reduced motion and offline app-shell caching.
9. Evaluate recognition, task performance, learning outcomes and usability using a repeatable study design.

## 5. Methodology

The project follows an iterative prototyping methodology. First, requirements were translated into screens, data structures and recognition fallback rules. Next, a mobile-first interface and modular JavaScript components were implemented. Equipment descriptions, parts, steps, warnings and quiz answers are maintained in `data/equipment.json`. A validation function checks required fields and references before an item is admitted to the interface. The recognition cascade attempts the optional classifier, checks QR frames, and leaves manual selection available regardless of model availability. A usability and learning evaluation should then compare the application with the existing paper/manual workflow.

### Content verification procedure

Each equipment entry should be reviewed by a qualified subject instructor or laboratory technician against the equipment manufacturer's documentation and the institution's SOP. Record reviewer, review date, source document and revision in the project maintenance log. The prototype schema does not yet enforce provenance metadata; this should be added before institutional deployment.

## 7. Implementation

### 7.1 Technology

- HTML5 semantic sections and form controls.
- CSS variables, responsive layout and reduced-motion support.
- JavaScript ES modules without a build process.
- `getUserMedia` for rear-camera or webcam access.
- TensorFlow.js 4.22.0 and Teachable Machine Image 0.8.5 for optional classification.
- jsQR 1.4.0 for QR decoding.
- `localStorage` for settings and feedback.
- Service Worker Cache API for the app shell and JSON dataset.

### 7.2 Recognition logic

The application loads the optional model only when `modelURL` is configured. If the model URL is empty or the library/model fails to load, recognition continues with QR scanning and manual selection. A QR payload is matched against an equipment `id`. AI predictions are matched against an equipment `name` or `id`; the app asks the user to confirm the proposed match. Predictions below 0.80 are never automatically accepted. In the current prototype, all AI matches require confirmation regardless of confidence.

### 7.3 Overlay and guidance

The overlay is a 2D SVG layer whose coordinates are percentages within a fixed alignment frame. The user aligns the physical instrument with a generic silhouette. It does not estimate camera pose, depth or object geometry. The guide displays the active part, step text, progress ticks and any warning. A warning checkbox enables the next-step control only after acknowledgement.

### 7.4 Quiz and feedback

The quiz displays one question at a time and reveals the correct answer and explanation after selection. The result screen calculates percentage correct. The five-item feedback form records responses locally and exports CSV. The five items are SUS-inspired, not the standardized ten-item System Usability Scale; do not calculate or report a conventional SUS score from them.

## 9. User study design

### Participants and ethics

Recruit 10–20 college students who have completed the relevant laboratory safety induction. Obtain informed consent, avoid collecting names or student IDs, and obtain institutional approval where required. Participation must not replace required safety instruction.

### Study design

Use a counterbalanced within-subject design where feasible. Each participant completes comparable equipment-identification and procedural-learning tasks using (A) the LabLens guide and (B) the institution's paper/manual method. Randomize or counterbalance the order to reduce practice effects. Provide the same safety briefing and task conditions to both groups.

### Measures

- Time to identify equipment and locate required parts.
- Number and type of procedural errors, assessed against an instructor-approved checklist.
- Number of safety-critical errors (report separately; do not combine with minor errors).
- Quiz score immediately after each learning condition.
- Task completion rate and requests for help.
- Usability ratings. If a validated SUS score is required, administer the full standard ten-item SUS with its established wording and scoring procedure; the app's built-in five-item survey is only supplementary feedback.
- Optional qualitative comments about clarity, confidence and confusing interactions.

### Analysis

Report participant count, missing data and descriptive statistics. For paired measures, calculate within-participant differences and use an appropriate paired statistical test after checking assumptions. Report effect sizes and confidence intervals, not only p-values. Preserve anonymity and store research data securely according to institutional policy.

## 11. Limitations

1. The overlay is a marker-aligned 2D guide, not true 3D tracking or markerless AR.
2. Hotspot positions are generic and do not adapt to object pose, scale or perspective.
3. Recognition accuracy depends on training image diversity, device camera quality, lighting and background.
4. The sample dataset contains only three equipment types and must be reviewed for local SOP compatibility.
5. Browser camera access requires HTTPS or localhost and user permission.
6. CDN scripts and fonts may be unavailable offline; manual functionality is the dependable fallback.
7. The service worker caches the application shell and data, not a guaranteed offline copy of every third-party model resource.
8. The five-item survey is not the standard SUS questionnaire.
9. The system cannot verify whether a user physically performed a step correctly.
10. This prototype is not a replacement for qualified supervision, risk assessment, safety training or manufacturer instructions.

## 12. Future work

- Add instructor-authored provenance, revision dates and approval status to every equipment record.
- Add a dataset management interface with schema validation and preview.
- Train and evaluate a larger model with a held-out multi-lab dataset.
- Add QR/visual fiducial tracking or WebXR-based spatial anchoring where device support permits.
- Support institution-specific procedures, multilingual content and accessible narration.
- Add a teacher dashboard and anonymized aggregate analytics with consent.
- Improve offline model delivery by hosting and caching approved model assets locally.
- Conduct a larger controlled study across different courses and experience levels.

## 13. Conclusion

LabLens demonstrates a modular, no-build approach to a camera-assisted laboratory field guide. Its fallback recognition design keeps the equipment library accessible when machine learning or QR scanning is unavailable. The separation between recognition and verified JSON instructions reduces the risk of AI-generated safety content. The current overlay is intentionally described as a 2D alignment aid. Further content review, model testing, usability evaluation and institutional validation are required before any operational laboratory use.

## 16. Viva questions and answers

**1. What is LabLens?**  
A mobile-first web application that identifies selected laboratory equipment and presents verified part information, safety-aware steps and a quiz.

**2. Why is it called AR-style rather than full AR?**  
It overlays labels in a camera interface using fixed 2D percentages. It does not estimate pose or anchor objects in 3D space.

**3. What is the recognition fallback order?**  
Optional Teachable Machine image classification, QR scanning using jsQR, and manual selection.

**4. Why is manual selection important?**  
It ensures the guide remains usable when camera permission, network access, a model or QR decoding is unavailable.

**5. What is Teachable Machine?**  
A browser-based tool for training simple machine-learning models, including image classification models exportable to TensorFlow.js.

**6. What is TensorFlow.js?**  
A JavaScript library for running and training machine-learning models in browser and Node.js environments. LabLens uses it through the Teachable Machine image library.

**7. How does QR recognition work?**  
The camera frame is drawn to a canvas, jsQR decodes the image and the returned text is matched to an equipment ID in the JSON dataset.

**8. Why is the content stored in JSON?**  
It separates content from application logic, making it possible to add or update equipment without rewriting the interface code.

**9. How are malformed entries handled?**  
A validator checks required properties, part coordinates, step references, warning types and quiz structure. Invalid entries are skipped and logged.

**10. How are safety warnings enforced?**  
For a step with a warning, the Next button is disabled until the user checks the acknowledgement control.

**11. What is a service worker?**  
A browser script that can intercept network requests and cache resources, allowing the app shell and equipment JSON to load after an initial online visit.

**12. Why does camera access require HTTPS?**  
`getUserMedia` is restricted to secure contexts, with localhost treated as a development exception by modern browsers.

**13. What is the 0.80 confidence threshold?**  
It is a conservative UI threshold used to distinguish lower-confidence suggestions. The app still asks the user to confirm every classifier match; it never treats confidence as proof.

**14. Is the built-in survey a standard SUS test?**  
No. It is a five-item SUS-inspired feedback form. A validated SUS score requires administering and scoring the standard ten-item questionnaire.

**15. What are the major limitations?**  
The 2D overlay is not true 3D tracking; model performance depends on data and lighting; browser camera access needs permission and HTTPS; and all safety content requires local expert review.
